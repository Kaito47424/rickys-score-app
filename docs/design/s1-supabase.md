# S1: Supabase移行

## 最終ゴール（アーキテクチャ）
GASを完全に廃止し、以下の構成にする。

```
ブラウザ → Vercel（React + Serverless Functions） → Supabase(Postgres)
```

そこへ至るまでのリスクを抑えるため、**GASを残したまま段階的に移行する**。
S1-1〜S1-5（並行書き込み）はその第一段階であり、最終形ではない。

## 移行方針（全体）
1. **並行書き込み**（S1-1〜S1-5・完了）: スプシへの書き込みは残したまま、GASからSupabaseにも同時書き込み。読み取りは当面スプシのまま
2. **安定運用の確認**（S1-6）: 実際のスコアリング運用でミラーが崩れないことを一定期間かけて確認
3. **読み取りロジックの移植**（S1-7）: 個人成績・各試合・年度別集計（打率・OBP/SLG・走者あり/なし打率・POP・K%・MVP集計等）をSupabase向けに実装
4. **APIのVercel移植**（S1-8）: `gas/rickys-api.gs`のdoGet/doPostが担う全機能をVercel Serverless Functions(`app/api/*`)へ移植し、フロントの参照先を切り替える
5. **GAS廃止・完全カットオーバー**（S1-9）: GAS Webアプリデプロイを停止し、Vercel+Supabaseのみの構成にする

## S1-6 検証チェックリスト

S1-5で確認したのは「移行時点の過去データがGASとSupabaseで一致すること」のみ。
S1-3/S1-4のミラューフックのうち、実運用で動作確認できているのは`_logEdit`
一箇所だけ（手動テスト`_testSupabaseMirror`）。残り5箇所は一度も実際の
スコアリングを通していないため、S1-7（読み取り移植）に進む前に以下を確認する。

### A. 書き込み経路ごとの実運用確認
実際に試合を1件動かしながら、各操作のたびに`scripts/verify-supabase-mirror.mjs`
を実行し差分が出ないことを確認する。

- [ ] `createNewGame()` — 新規試合作成 → `games`テーブルに反映されるか
- [ ] `_apiSaveRoster` — スタメン保存 → `roster_entries`に反映されるか
- [ ] `_apiInning` — イニング送信（打席結果・相手攻撃・打点等） → `bat_results`/`pitch_results`/`batter_manual_stats`/`pitcher_appearances`に反映されるか（一番使用頻度が高い経路）
- [ ] `_saveMvp` — MVP入力 → `mvp`に反映されるか
- [ ] `_logEdit` — 修正履歴発生 → `edit_log`に反映されるか（テスト済み・実運用でも再確認）
- [ ] `_deleteGame` — 試合削除 → `games.deleted_at`に反映されるか

### B. データ特有のエッジケース
- [ ] 選手交代がある試合で`sub_from_inning`が正しく保存されるか（GASのスプシには保存されない値のため、初めて本番で永続化されるデータ。特に注視）
- [ ] 助っ人（選手マスタに無い選手）が`player_id=null`＋名前のみで正しくミラーされるか
- [ ] 失策(遊)等のエラーコードが`bat_results`に正しく入り、`失策出塁`集計に影響しないか
- [ ] 同じイニング/打順への複数回送信（入力し直し）で、重複行ができず正しく上書き（upsert）されるか

### C. 耐障害性
- [ ] スクリプトプロパティを一時的に空にする、または誤った値にした状態でイニング送信を行い、**スプシ側の書き込みが今まで通り成功すること**を確認（ミラー失敗が本体に影響しない設計の裏付け）
- [ ] GASを`clasp deploy`で再デプロイしてもスクリプトプロパティ（Supabase接続情報）が消えないことを確認（プロパティはデプロイと別管理のため通常は影響ないが、念のため）

### D. 既知の制約（今回は検証不要・仕様として認識しておく）
- 投手別集計セクションは相手攻撃シート自体が物理的に7行までしかないため、
  Supabase側の`pitcher_appearances`はキャップを設けていなくても、**現行のスプシ
  運用が続く限り実際に8人目の投手が記録されることはない**。この制約はS1-8
  （API移植）でスプシ非依存の入力方式にしない限り解消されない。

### 完了の目安
実際の試合を3〜5件程度、上記A〜Cを問題なく通過してから安定運用と判断し、
S1-7（読み取りロジック実装）に着手する。
